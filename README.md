# Book Fetcher

اسکریپتی که از API عمومی OpenLibrary تعداد مشخصی کتاب دریافت می‌کند، آن‌هایی که بعد از یک سال مشخص منتشر شده‌اند را فیلتر می‌کند و نتیجه را در یک فایل CSV ذخیره می‌کند.


## ساختار پروژه

```
book-fetcher/
├── api/
│   └── api_client.py      # ارتباط با OpenLibrary API
├── utils/
│   ├── config.py           # خواندن مقادیر از config.json
│   ├── filters.py          # فیلتر کتاب‌ها بر اساس سال انتشار
│   └── csv_writer.py       # نوشتن خروجی در CSV
├── output/
│   └── fetched_books.csv   # خروجی نهایی (تولید می‌شود موقع اجرا)
├── config.json              # تنظیمات قابل تغییر
├── main.py                  # نقطه شروع برنامه
├── requirements.txt
└── .gitignore
```

هر فایل یک مسئولیت مشخص دارد تا خواندن و دیباگ کردن کد ساده باشد: `api_client.py` فقط با API صحبت می‌کند، `filters.py` فقط فیلتر می‌کند، `csv_writer.py` فقط می‌نویسد، و `main.py` فقط این سه مرحله را پشت‌سرهم صدا می‌زند.

## تنظیمات (config.json)

همه‌ی مقادیر قابل تغییر برنامه در یک جا نگه‌داری می‌شوند تا داخل کد هیچ عدد یا رشته‌ی ثابتی (magic value) وجود نداشته باشد:

```json
{
  "openlibrary_search_url": "https://openlibrary.org/search.json",
  "search_query": "book",
  "fields": "*",
  "fetch_limit": 50,
  "request_timeout": 15,
  "year_cutoff": 2000,
  "output_csv_path": "output/fetched_books.csv"
}
```

فایل `utils/config.py` مسیر این فایل را با `pathlib` پیدا می‌کند، آن را می‌خواند و مقادیرش را به‌صورت ثابت (constant) در اختیار بقیه‌ی ماژول‌ها قرار می‌دهد. `output_csv_path` هنگام خواندن با `Path(...)` پیچیده می‌شود تا در بقیه‌ی کد به‌صورت یک شیء `Path` واقعی استفاده شود، نه رشته‌ی متنی.

## جریان اجرا (main.py)

```
fetch_books()  →  filter_books()  →  write_books_csv()
```

1. **دریافت داده (`api/api_client.py`)**
   تابع `fetch_books(search_url, query, limit)` یک درخواست GET به endpoint جستجوی OpenLibrary می‌زند و فیلدهای `title`، `author_name` و `first_publish_year` هر کتاب را برمی‌گرداند.

   نکات مهم این بخش:
   - درخواست با `timeout` (خوانده‌شده از کانفیگ) ارسال می‌شود تا در صورت هنگ کردن سرور، برنامه برای همیشه منتظر نماند.
   - خطاها به‌صورت جدا مدیریت می‌شوند: `Timeout` جدا از بقیه‌ی خطاهای شبکه (`RequestException`) گرفته می‌شود تا پیام لاگ دقیق‌تر باشد.
   - در صورت شکست درخواست، تابع لیست خالی (`[]`) برمی‌گرداند، نه `None`؛ این باعث می‌شود بقیه‌ی برنامه بدون نیاز به چک اضافه بتواند روی خروجی حلقه بزند.
   - در ابتدای کار برای `search_query` از مقدار `"the"` استفاده شده بود و درخواست همیشه با ارور ۴۲۲ و صفر کتاب برمی‌گشت. اول تصور شد مشکل از عدم ارسال هدر `User-Agent` است (چون OpenLibrary گاهی درخواست‌های بدون User-Agent را رد می‌کند)، اما بعد از اضافه کردن هدر هم مشکل حل نشد. با چاپ کردن بدنه‌ی واقعی پاسخ خطا (`response.text`) مشخص شد که مشکل واقعی جای دیگری بود: خود OpenLibrary کوئری‌های خیلی عمومی مثل `"the"` را مستقیماً رد می‌کند (`Invalid query`). با تغییر `search_query` به یک مقدار معنادارتر مثل `"book"` مشکل برطرف شد.

2. **فیلتر کردن (`utils/filters.py`)**
   تابع `filter_books(books, year_cutoff)` روی لیست خام کتاب‌ها حلقه می‌زند و فقط آن‌هایی که `first_publish_year` بزرگ‌تر از `year_cutoff` دارند را نگه می‌دارد. اگر کتابی اصلاً فیلد سال انتشار نداشته باشد، با `book.get("first_publish_year", 0)` مقدار پیش‌فرض ۰ در نظر گرفته می‌شود تا برنامه کرش نکند و آن کتاب به‌طور طبیعی از فیلتر رد نشود.

3. **نوشتن خروجی (`utils/csv_writer.py`)**
   تابع `write_books_csv(books, path)` لیست فیلترشده را با `csv.DictWriter` در فایل CSV می‌نویسد.

   **چرا ستون‌ها به‌صورت داینامیک ساخته می‌شوند:**
   در نسخه‌ی اول برنامه، لیست فیلدها (`title`، `author_name`، `first_publish_year`) به‌صورت مجیک‌نامبر داخل خود کد نوشته شده بود. بعد این لیست به کانفیگ منتقل شد تا ثابت نباشد. اما وقتی مقدار `fields` در `config.json` روی `*` تنظیم می‌شود، OpenLibrary برای هر کتاب هر فیلدی که موجود باشد را برمی‌گرداند — و این فیلدها بین کتاب‌ها یکسان نیستند (مثلاً یک کتاب `isbn` دارد، کتاب دیگر ندارد). اگر لیست ستون‌ها از قبل ثابت باشد، این اطلاعات اضافه یا نادیده گرفته می‌شود یا باعث ناهماهنگی بین ردیف‌ها می‌شود.

   راه‌حل این بود که به‌جای یک لیست ثابت از فیلدها، **اجتماع (union)** تمام کلیدهایی که در کل کتاب‌های دریافتی وجود دارند ساخته شود:

   ```python
   fieldnames = set()
   for book in books:
       fieldnames.update(book.keys())

   fieldnames = list(fieldnames)
   ```

   یعنی هر کلیدی که حتی در یکی از کتاب‌ها دیده شود، به‌عنوان یک ستون در CSV نهایی ظاهر می‌شود.

   بعد از آن، مشکل بعدی این بود: حالا که ستون‌ها از روی همه‌ی کتاب‌ها ساخته می‌شوند، برای کتاب‌هایی که آن فیلد خاص را نداشتند باید سلول خالی نماند. این‌جا `csv.DictWriter` با پارامتر `restval="Unknown"` این کار را انجام می‌دهد:

   ```python
   writer = csv.DictWriter(f, fieldnames=fieldnames, restval="Unknown")
   ```

   `restval` مقداری است که `DictWriter` به‌صورت خودکار برای هر ستونی که در دیکشنری یک ردیف خاص وجود نداشته باشد جایگزین می‌کند. پس دیگر نیازی نیست دستی برای هر فیلد چک `.get(..., "Unknown")` نوشته شود؛ همین یک پارامتر همان کار را برای تمام ستون‌های ناشناخته انجام می‌دهد.

   نکات دیگر این بخش:
   - `if not books: return` قبل از هر کاری چک می‌کند که اگر لیست خالی باشد، برنامه سراغ ساختن فایل و پوشه نرود و فقط یک لاگ بزند.
   - `path.parent.mkdir(parents=True, exist_ok=True)` پوشه‌ی `output/` را در صورت نبودن می‌سازد، تا روی یک کپی تازه از ریپو هم بدون خطا اجرا شود.
   - `newline=""` هنگام باز کردن فایل استفاده شده تا در ویندوز بین ردیف‌های CSV خط خالی اضافه نشود.
   - `writer.writerows(books)` کل لیست را یک‌جا می‌نویسد، به‌جای حلقه زدن دستی روی هر کتاب.

## نحوه‌ی اجرا

### ویندوز

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python -m main
```

### لینوکس / مک

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m main
```

خروجی نهایی در مسیری که در `config.json` تحت `output_csv_path` مشخص شده (به‌صورت پیش‌فرض `output/fetched_books.csv`) ساخته می‌شود.

## لاگ‌گیری

به‌جای `print`، از ماژول `logging` استفاده شده تا هر مرحله (تعداد دریافت‌شده، تعداد باقی‌مانده بعد از فیلتر، مسیر فایل نوشته‌شده) به‌صورت شفاف در ترمینال نمایش داده شود و در صورت بروز مشکل، بلافاصله مشخص باشد کدام مرحله شکست خورده.
